有一天，我心血来潮问豆包：“你对我的了解是什么？觉得我是怎样一个人？”

没想到它居然根据过去的聊天，说出了不少关于我的信息。我的工作、居住城市、家庭成员，连我平时关注什么它都知道，具体得像一份持续更新的个人档案——关键还确实没说错。

更让我意外的是回答的最后，豆包表示，它不会记住手机号、身份证、家庭详细住址等信息，还称这些记忆只属于我们的对话、不会对外泄露。随后，它给了我三个选择：删掉某一条记忆、清空全部记忆，或者继续聊。

这让我开始好奇：Agent 是怎么记忆的？它把这些信息存在哪里，又是怎么在需要的时候想起来的？它还能选择性记忆吗？

## 01　Agent 的两种记忆

人的生活离不开记忆。我们记得刚刚说过的话，才能继续交流。Agent 同样需要记忆。如果它什么都记不住，我们每发一条消息，都要重新说明需求。任务稍微长一点，它还可能忘记之前的要求、丢掉进度，甚至重复调用工具。这样的 Agent 可以回答一个问题，却很难持续完成一件事。

人的记忆有远近之分，Agent 也一样。按照信息需要保留的时间，可以把 Agent 的记忆分为两种：**短期记忆**和**长期记忆**。

**短期记忆**是 Agent 为完成当前对话或任务而暂时保留的信息，比如用户输入了什么、模型输出了什么、工具调用返回了什么、任务进行到了哪一步等。它让 Agent 接得住上文，能够继续完成眼前的任务。

**长期记忆**是能跨越当前对话，在以后的任务中仍可继续使用的信息，比如用户较稳定的偏好、反复出现的习惯和长期项目背景等。任务结束后，这些信息仍然存在。下次需要时还能拿回来用，而不必从零开始了解用户需求。

| 对比项 | 短期记忆 | 长期记忆 |
|-|-|-|
| 时间范围 | 当前对话或当前任务 | 多次对话或不同任务 |
| 主要内容 | 最近对话、任务要求、工具返回结果、当前进度 | 稳定偏好、常用信息、可复用的任务背景 |
| 解决的问题 | 让 Agent 接着做，不丢掉眼前的事 | 让 Agent 下次还能用上过去的重要信息 |
| 典型例子 | “这份方案先比较三家公司，再给结论” | “我更喜欢先看结论，再看分析过程” |

无论是短期记忆，还是长期记忆，只有进入**当前上下文**，模型这一轮才能使用。当前上下文就是模型这一次实际看到的全部材料，可以理解为 Agent 此刻的工作桌面。Harness 会把当前任务需要的短期记录和相关的长期信息取出来，放到这张桌面上；没有放进来的内容，对模型来说就是看不见的。

也就是说，模型本身不会把上一轮内容自动留到下一轮；能表现出“记得”的，是模型与 Harness 共同组成的 Agent 系统。Harness 负责保存要求、进度和工具结果，并在需要时重新交给模型，Agent 才能接着原来的任务继续做，不至于忘记要求、丢掉进度或重复操作。把信息存下来只是起点，后面还需要一套完整的管理过程。

## 02　Harness 如何管理一条记忆

一条信息从产生、使用到遗忘，会经过五个环节，它们构成 Harness 管理记忆的全链路。

**1. 写入：决定该记什么**

信息可能来自用户明确提出的“请记住”，也可能由产品规则筛选、模型从对话中提取，或因为多次重复出现而进入候选。难点在于掌握分寸：既不能把每句话都变成记忆，也不能漏掉稳定偏好和关键约束。

**2. 保存：把信息变成可管理的记录**

写下来的内容需要整理后放入合适的载体。难点不只是把文字存下来，还要带上作用范围、来源、时间和附件关联，让系统以后能够找到、判断和修改它。

**3. 检索：找出当前任务真正需要的内容**

面对已有记录，Harness 要选出与眼前问题有关的部分。难点是同时兼顾查全与查准，并守住用户、项目和权限边界，避免过期信息或无关内容混进来。

**4. 注入：把选中的记忆交给模型**

检索到的信息还要经过整理，再放进当前上下文。难点是上下文空间有限，需要安排优先级和数量；过去的记忆可以补充背景，但不能压过用户这一次提出的新要求。

**5. 更新与遗忘：让记录跟上变化**

新信息出现后，旧记录可能需要修正、合并、失效或删除。难点是处理相互冲突的内容，并同步调整相关摘要和索引，避免已经变化的信息继续写入记忆。

这五个环节不是走完一次就结束。记忆被使用后，当前任务又会产生新信息，再次触发写入、保存或更新，形成一个持续循环的过程。

接下来，就结合现有 Agent 的实际做法，看看这五个环节在工程中是怎样运转的。

## 03　该记什么，如何保存？

链路的起点是写入。Harness 先要判断哪些内容值得保留，再决定以什么形式保存、存在哪里。**不是所有发生过的事都值得记住——存错了，比不存更糟。**没记住，用户顶多再说一遍；记错了，这条信息可能在以后每次相关任务中被重新取回，持续影响 Agent 的回答和行动。

### 短期记忆记什么，存在哪？

**短期记忆主要服务当前任务。** Harness 会把当前会话里的用户消息、模型回复、工具调用和工具结果记录在**会话状态**中。每次调用模型前，Harness 再从这些记录中整理出模型这一轮实际能看到的**当前上下文**。

为了便于理解，先看一条基于 DeepSeek Harness 的原始数据结构简化的 JSON 伪记录：

```json
{
  "session_id": "sess_001", // 这次会话的编号
  "events": [ // 会话中发生的事情，按顺序排列
    { "seq": 1, "type": "user/message", "content": "帮我比较三家公司" }, // 用户消息
    { "seq": 2, "type": "assistant/message", "content": "好，我先查资料" }, // 模型回复
    { "seq": 3, "type": "tool/call", "call_id": "call_01", "content": "搜索资料" }, // 发起工具调用
    { "seq": 4, "type": "tool/result", "call_id": "call_01", "content": "返回搜索结果" }, // 工具返回结果
    { "seq": 5, "type": "assistant/message", "content": "三家公司的差异是……" } // 模型继续回答
  ]
}
```

`seq` 表示事件的先后顺序。`type` 标明这是一条用户消息、模型回复、工具调用还是工具结果。`call_id` 像一次工具调用的编号，把发出的调用和返回的结果配成一对，避免与其他调用混淆。

DeepSeek Harness 会为每次会话建立一个 `Session`（会话对象）。事件先保存在内存中。如果产品配置了会话文件保存组件，这些事件还会写进该会话对应的 **JSONL** 文件。JSONL 可以理解为“一行保存一条事件”的文本文件。

以后继续同一会话时，产品可以使用原来的 `session_id` 读回这些事件，重新组成 `Session`。这里恢复的仍是原来那次会话的短期记录，不会因为写进文件，就自动变成经过筛选和整理的跨任务长期记忆。

### 哪些内容值得长期保留？

**相比于短期记忆，长期记忆则不同。它要跨任务继续使用，因此 Harness 必须进一步判断：哪些信息值得进入长期记忆，哪些只是当前任务中的临时内容。**内容比较稳定、以后还会用到的信息才值得留下，比如用户明确表达的长期偏好、持续有效的个人事实，或需要跨任务跟进的事项。寒暄、无关内容和一次性要求不必长期保存，涉及隐私的敏感信息也不能因为在对话中出现过就默认写入。已有记录中，重复的可以合并，互相冲突的则要先核对，再决定是否更新。

Codex 的长期记忆写入也不是“说一句、记一句”。它先从近期任务中挑出与长期使用有关的内容，再让模型整理成详细记忆和任务摘要；如果没有值得留下的信息，这次提取可以不产生结果。之后，多个任务产生的候选还会再次合并，才形成可供未来任务使用的记忆。

![长期记忆筛选](/images/article-content/agent-memory11/03-long-term-memory-screening.png)

### 不同资料分别存在哪里？

先看一条长期记忆在工程上可能长什么样。用户偏好、任务事实等适合按字段管理的信息，可以被整理成带有固定字段的记录。下面是一条简化的 JSON 伪记录：

```json
{
  "memory_id": "mem_001", // 这条记忆的唯一编号，便于查询、更新和删除
  "user_id": "user_001", // 标明这条记忆属于哪位用户
  "content": "解释技术概念时，先给出大白话概述", // 真正需要被记住的内容
  "type": "表达偏好", // 说明这条内容属于哪一类信息
  "scope": "与这位用户的技术学习对话", // 限定这条记忆在哪些任务或场景中生效
  "source": "用户明确提出", // 记录信息从哪里来，方便以后回查依据
  "status": "有效", // 标明这条记忆目前是否仍能继续使用
  "updated_at": "2026-10-06", // 记录最近更新时间，帮助判断信息是否过时
  "confidence": "高" // 表示这条信息目前有多可靠
}
```

这只是长期记忆的一种保存形式。实际需要保存的可能不止这一种：有的字段固定，有的只有部分字段固定，还有长文、图片、音频等没有固定结构的内容。它们的大小、更新方式和读取方式差别很大，权限要求也可能不同。因此，工程上通常会让多种存储方式分工配合，而不是把所有内容一股脑塞进同一个“记忆库”。

- **结构化信息**的字段大多事先确定，像一张列名固定的表格。用户 ID、记忆类型、生效场景、更新时间等内容，可以放在关系数据库中，方便按字段查询和更新；需要凭 `session_id`、`user_id` 或 `memory_id` 直接取回的记录，也可以放进 Key-Value 存储——它像一排带编号的抽屉，知道编号就能直接拉开。
- **半结构化信息**有基本框架，但每条记录的字段可以增减。例如，偏好记录可能带有来源，跟进事项还会多一个截止时间。这类内容可以放在文档数据库中，以 JSON 文档等形式保存，像一份每页都能增减栏目的档案。
- **非结构化资料**很难靠一组固定字段完整表达，例如长文、PDF、图片、音视频等。它们的原件通常放在文件系统或对象存储（可以理解为专门保管大文件的“云端文件仓库”）中；数据库只记录文件 ID、地址、权限等相关说明，用来把原件与用户或任务连起来。比如同一份 PDF 可以把原件放在文件或对象存储中，同时在数据库里留下一条记录，再通过同一个文件 ID 建立关联。

## 04　怎么检索，怎么注入？

记忆保存下来，并不等于模型已经能用。Harness 还要决定什么时候发起检索，从已有记忆中找出候选信息，再经过筛选和整理，把真正相关的内容放进当前上下文。少了其中任何一步，模型要么看不见过去的信息，要么会被不该出现的内容干扰。

### 检索什么时候发生

一种方式是**预先加载**。像一个熟悉的助理，你还没开口，他已经把你常要的几份材料从档案柜里取了出来——任务开始前，Harness 根据已经知道的用户、项目和应用规则，先把少量稳定、经常需要的信息取回来，不用等用户明确提出“请回忆”。它适合范围清楚、使用频率较高的内容。

另一种方式是**按需检索**。像是你临时问起三个月前的一份合同，他才起身去柜子里翻。当前问题确实需要过去的信息时，系统才开始查找。触发信号可以来自用户的请求，也可以是 Harness 的规则识别到相关主题，或者模型判断信息不足并调用记忆工具。

### 怎样找出候选记忆

触发检索以后，Harness 才进入具体的查找。常见手段包括：

**1. 按 ID 精确读取**

已经知道正确 ID 时可以直接读取对应记录。ID 是一条会话、文件、项目或记忆记录的唯一编号，Harness 直接按它取回对应内容，不需要在一堆记录里挑。

**2. 按元数据过滤**

不确定 ID，但知道大概范围时可以先按元数据缩小范围。元数据是和记忆一起保存的附加信息，例如所属用户、项目、类型、时间和权限等。Harness 先用这些字段排除不属于当前用户、项目或权限范围的记录，再在剩下的里面找。它只负责把范围划小，不决定最后留下谁。

**3. 按关键词搜索**

问题里出现明确的名称、编号或固定说法时，可以按这些词去找包含它们的记录。为了不用逐条翻找，系统会提前建立一张“关键词 → 记录位置”的对照表，查询时顺着词找到原记录，这在工程上叫作**倒排索引**。这种方法速度快，但依赖用词重合，换个说法可能就找不到。

**4. 按语义搜索**

两段文字用词不同、但意思相近时可以按照语义进行检索。系统先通过 **Embedding（向量表示）**把文本转换成一组代表语义的数字，再用**向量索引**找出位置相近的内容——就像把每段文字标在一张“语义地图”上，意思越近，位置越近。向量索引只是找到原文的路径，不是记忆本身；语义相近，也不能保证用户、项目、权限和时间范围都对。

这四种只是常见手段，不是必须采用的完整统一分类；实际系统通常几条一起用，顺序也不固定，下图画了一种常见的组合。

### 最终还要经过筛选和注入

查找返回的通常是一组候选记录，不能直接全部交给模型。

首先要剔除已经过期、来源不可靠或彼此矛盾的信息，去掉重复；再按与当前任务的相关程度和时效排一遍，设一个保留门槛；最后留下的如果太长或太多，只摘出能影响当前决策的部分，控制数量，避免挤占用户这一次的新要求。

整理后的内容通常从两类位置进入当前上下文。第一类是在任务或模型调用开始前，放进系统提示词（产品预先写好的角色和规则），或单独的记忆上下文块；第二类是在模型调用记忆工具后，以工具结果进入下一轮上下文。无论采用哪种位置，只有完成注入，模型这一轮才真正看得见这些记忆。

Codex 把这两种入口组合在一起：新任务开始时，一份精简的记忆摘要会先放进当前上下文；当任务需要更多细节时，Agent 再按需查找完整记忆和过去的任务摘要。因此，全部长期记忆不必一次性塞给模型。

下面是根据 Codex 真实源码整理的简化伪代码：

```text
function prepare_task_with_memory(user_request):
  // ① 摘要提前注入
  // 读取精简记忆摘要，并按允许的最大长度截短
  summary = read("memory_summary.md")
  summary = truncate_by_tokens(summary, TOKEN_LIMIT)
  // 放进任务开始前的指令区，模型处理当前问题时会先看到
  developer_instructions.add(summary)
  context = [developer_instructions, user_request]

  // ② 细节按需检索并注入
  while task_not_finished:
    output = call_model(context)
    if output is search_or_read_tool_call:
      // 摘要不够时，再查完整记忆和过去的任务摘要
      details = run_memory_tool(output)
      // 检索结果进入下一轮上下文
      context.add(output)
      context.add(details)
      continue
    return output
```

## 05　何时更新，何时遗忘？

人的记忆会被新的事情慢慢覆盖，也会随时间逐渐淡忘，Agent 也是如此。不过，Agent 的“遗忘”不是大脑自然淡忘，而是 Harness 主动更新、标记失效或删除记录。

信息本身会变化。偏好会改，任务会结束，昨天的结论今天可能就不成立。记下来的东西，不会因为存住了就一直是准的。

记忆也不是越多越好，记录保留过多会带来两个问题。一是造成检索困难。记录越多，候选越多，越难挑出真正相关的那几条，错误和过期的内容也越容易被一起带上来；二是上下文冗长。能交给模型的空间就那么大，旧信息放多了，用户这一次的新要求就被挤掉。

所以，一套能长期使用的记忆机制，不能只负责“记住”：信息发生变化时，要及时更新；信息已经失效时，也要让它退出。下面展开讲解：

1. **新旧信息冲突时怎么办**

新信息不会无条件覆盖旧信息。Harness 要先判断两条记录说的是不是同一个对象、是否适用于同一个范围，再结合来源、时间和可信程度处理。

同一对象、同一范围，而且新来源更可信，就更新旧记录。例如，Agent 之前记着用户每周三晚上去健身，后来用户明确说今后改到周六上午。

范围不同，就标清范围并让两条记录同时存在。例如，长期记录是“平时出行优先坐地铁”，但用户这次因为带着两个大箱子，明确要求打车去机场，一个是长期偏好，一个是当前任务的要求，不必互相覆盖。

如果来源、范围或时间关系说不清，就降低可信度、标记冲突并暂缓使用，必要时再请用户确认。

1. **哪些记忆应该清理**

需要清理的通常是四类：用户明确要求删除或清空的；已经确认错误、又没有保留价值的；任务结束后便失效的一次性状态、临时约束和短期事实；以及内容完全重复或者已经被别的记录完整包含的。

其中，任务结束后失效的那一类通常不需要人判断——保存时就可以给它设一个有效期，也就是 TTL（Time to Live，存活时间）。对于“本周出差”、“明天下午取快递”这类信息，Harness 在写入时就标好到期时间，计时和清理可以交给底层数据库；到期后，记录先退出正常检索，再按产品策略清理。

长期没有再被使用、也看不出复用价值的信息，可以根据具体产品的保留策略成为清理候选，而不是一律立即删除。

真实系统采用的清理方法并不相同。Codex 会结合记忆的使用次数、最近使用时间和最长闲置时间，决定哪些内容继续进入下一轮整理；LangGraph 则把 TTL 做成可选能力，只有存储后端支持并明确设置时才会过期。TTL 管的是“保留多久”，并不负责判断两条冲突信息该信哪一条。

1. **处理时具体做什么**

具体有三种方式：**更新或合并**，是让新内容接替旧内容，或把仍然有效的部分整理到一起；**标记失效**，是保留历史记录，但不再让它进入正常检索；**真正删除**，则是移除记录以及找到它的路径。

无论采用哪种动作，相关的摘要、检索索引和缓存都要同步更新，否则旧信息仍可能被再次找回。

## 06　小结

假设用户让一个 Agent 帮忙规划周末旅行：“去苏州两天，预算 1500 元，周日下午 5 点前回上海。”用户直接使用的是一个完整的 Agent。这里的 Agent 是对外呈现的完整系统，模型和 Harness 是其中承担不同职责的两部分，它还会连接工具和外部记忆存储。整条链路可以如下图展开：

![Agent 记忆链路](/images/article-content/agent-memory11/06-agent-memory-chain.png)

这张图把短期记忆和长期记忆的关系串了起来：短期记忆留在当前任务里，长期记忆保存在上下文之外；但长期记忆只有被找回，并和这次任务的要求、工具结果、当前进度一起放进上下文，模型才能真正用到它。保存只是起点，真正让记忆发挥作用的，是 Harness 能否在合适的时候把合适的信息交给模型。

再回到开头那次豆包对话。要形成“它很了解我”的体验，系统不仅要在过去留下信息，还要在这次提问时把相关内容重新带回来。用户感受到的是 Agent“记得我”，背后发生的其实是一整套信息管理：什么值得留下，什么时候需要出现，信息发生变化后又该怎样处理。它说不会记住手机号、住址，也是同一套机制的一部分：不是记不住，而是写入时就判断过——这些内容不该留。

因此，一套可靠的 Agent 记忆系统，不是记得越多越好，而是让该出现的信息在合适的时候出现，让过时的信息及时更新，让不该保留的内容能够被删除，并把纠正记忆的权利留给用户。
