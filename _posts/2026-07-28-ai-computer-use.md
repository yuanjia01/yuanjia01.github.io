![Codex 与 ChatGPT Work 周活增长曲线](/images/article-content/blog04/xblog.png)

## 01 我先把博客交给 Codex

我之前已经用 OpenCode 搭建并上线了个人博客。第一次看到 `yuanjia01.github.io` 能被任何人访问时，我很有成就感，因为它意味着本地的一堆文件，终于变成了一个真正存在于互联网上的网站。

不过，网站上线一段时间后，我开始注意到另一个问题：它可以正常展示文章，却还不像一个“个人空间”。头像、名称和内容都有了，但页面的配色、留白、字体和结构依然延续着基础模板，看不出我的偏好，也没有形成稳定的视觉记忆。

这个博客改造很适合作为我尝试 Codex 的第一个真实任务：**它既要理解现有代码，又要处理“温馨”、“治愈”、“有生命力”这些没有标准答案的设计语言。**我没有准备设计稿，也没有指定字号、间距和色号，只给了它一段接近日常表达的需求：

```text
这是我的个人博客，请先在本地运行并学习网站现有内容。

我想把它改成温馨治愈的森系个人博客。
我喜欢绿色这种有生命力的颜色，希望有轻微动画。

网站名称保留 Gia's Blog。
先做出本地预览，我确认后再推送到 GitHub。
```

## 02 浏览器自己动了起来

收到需求后，Codex 没有直接生成一套与原项目无关的新页面，而是先读取博客本地代码库，检查项目结构、配置文件、文章布局、图片资源和当前使用的 Jekyll 模板。随后，它在本地启动网站，通过浏览器查看原来的首页与文章页，确认哪些内容需要保留、哪些视觉部分可以重新设计。

我原本以为，它会一直待在命令行里：读取文件、修改 CSS、运行构建命令，然后告诉我“已经完成”。但实际过程中，它触发了 Computer Use，打开本地网页并检查真实呈现效果，还会滚动页面、查看不同区域和移动端布局。也是从这个时候开始，我第一次认真注意到 Computer Use——**原来 Codex 不只是会修改网页代码，还会自己打开浏览器了解改造前的页面现状，并检查任务完成后的实际效果。**

![Computer Use 打开并检查博客页面的过程](/images/article-content/blog04/computer-use-blog-replay.gif)

在理解现有内容后，它重新设计了首页欢迎区、文章卡片、导航栏、正文页和页脚。配色以森林绿、鼠尾草绿和米白色为主，背景增加了柔和光晕与纸张质感；动画则控制在叶片轻摆、背景呼吸和卡片淡入上，不会干扰文章阅读。

## 04 AI 真的看见了网页吗？

第一次看到 Codex 打开浏览器、滚动页面时，我最想确认的问题是：AI 真的看见了网页吗？**答案是“看见了”，但这种看见与人类持续注视屏幕并不完全一样。**进一步了解后我发现，Computer Use 获得的是任务过程中不断更新的屏幕截图。

它的工作方式可以概括为一个循环：系统先截取当前画面，模型通过视觉能力理解页面上的文字、按钮和布局，再决定应该点击、滚动还是输入内容。操作执行以后，系统会返回一张新的截图，模型根据页面变化继续判断下一步，直到任务完成或遇到需要人工确认的环节。

这很像我们在远程指导一位朋友操作电脑：他先发来一张屏幕照片，我们告诉他应该点击哪里；操作之后，他再发一张新照片，我们确认结果并给出下一步指令。在这个过程中，模型负责“看”和“判断”，运行环境负责代替鼠标与键盘执行动作，两者共同形成“截图—理解—操作—新截图”的闭环。

1. **感知：**获取当前屏幕截图，了解电脑此刻的状态。
2. **推理：**结合任务目标和之前的操作，决定下一步做什么。
3. **行动：**执行点击、滚动或输入等操作。
4. **反馈：**查看新的截图，确认变化后继续或停下。

![Computer Use 的“感知—推理—行动—反馈”循环](/images/article-content/blog04/ChatGPT-Image-CUAloop.png)

因此，说 AI 看见了网页并不是修辞，只是这里的“看见”是工程意义上的视觉理解。它并不是躲在命令行背后假装看见，而是确实接收了页面截图，并从像素中理解界面元素与当前状态。对我来说，最颠覆认知的并不是它会点击，而是它每执行一步都会重新观察页面，并根据眼前的变化决定下一步。

## 05 为什么还需要“看”屏幕？

弄清楚 Computer Use 是通过截图理解页面后，我又想到一个更实际的问题：**既然 AI 已经能直接调用 API、执行 CLI 命令，为什么还需要像人一样“看着屏幕”操作？**

API 像软件之间提前约定好的专用窗口，程序按照规则提交数据，就能直接得到结果；CLI 则是用文本命令操作软件，适合修改文件、运行程序和管理项目。MCP 可以把这些可用的数据和工具统一介绍给 AI，让模型知道自己能调用什么、需要提供哪些参数。它们的共同点是操作路径已经被定义好，AI 不必先观察屏幕再寻找入口。

回到这次博客改造，CLI 与 Computer Use 的分工就更直观了：CLI 用来读取和修改本地代码、执行构建命令，Computer Use 则用来观察并操作网页。Codex 先读取博客本地代码库，了解项目结构和文章内容，又用 Computer Use 打开旧网站，滚动查看首页、文章页和完整页面范围，弄清原有样式以及哪些内容需要保留。完成这些准备后，它才通过 CLI 修改代码、运行本地构建，再次用 Computer Use 检查改造后的配色、间距、文章卡片和手机端布局，并根据看到的问题继续调整。**整个过程在“理解旧页面—修改代码—查看新页面—继续调整”的循环中不断切换。**

很多任务恰好停留在后一种情况里：人只要看一眼页面，就知道按钮在哪里、布局是否错位、弹窗有没有出现，但软件之间没有现成的接口可以直接交换这些信息。Computer Use 的价值，就是把这部分原本只能由人完成的视觉判断和界面操作，也交给 AI 一步步处理。

所以，Computer Use 并不是为了取代 API、CLI 或 MCP，而是补上它们到不了的那一段。

## 06 当 AI 开始像人一样使用电脑

这次改造博客让我真正意识到，Computer Use 带来的变化，并不只是让 AI 多了一只能够点击的“虚拟鼠标”。它更重要的能力，是像人使用电脑一样，先观察当前页面，分析按钮、输入框和页面内容，再决定点击、输入还是滚动。每完成一个动作，它都会重新查看变化后的画面，并根据新的状态继续下一步。

这种工作方式与执行一条预先写好的脚本不同。脚本知道的是固定流程，而 Computer Use 面对的是不断变化的界面：弹窗可能突然出现，按钮位置可能发生改变，页面加载也可能比预期更慢。AI 需要一边操作，一边判断自己有没有走对，并在必要时调整路径。**它不只是“按下按钮”，而是在界面中持续观察、尝试和修正。**

看着 Codex 在页面与代码之间来回切换，我也不禁想到：有了 Computer Use，从事美工、网页设计等相关工作的人，未来会怎样与 AI 协作？过去让 AI 写网页，往往停在“生成代码”这一步，最终效果是否舒服、留白是否合适、移动端有没有错位，仍然要由人打开浏览器逐项检查；有了 Computer Use，AI 可以回到真实页面观察结果，再根据视觉反馈继续调整。审美方向仍由人给出，但“提出方向—实现页面—查看效果—继续修改”这条反馈链被明显缩短。对我这种没有专业设计背景的人来说，我不必先把“森系”翻译成精确的色号、字号和间距，只要说清楚想要的感受，就能围绕真实页面继续调整。这简直把网页设计的表达门槛又降低了一层：即使不懂代码、不熟悉专业设计参数，也可以先说清楚自己想要的感觉，再和 AI 围绕真实页面一点点把它做出来。

**Computer Use 让 AI 能够看见并理解当前界面，判断下一步该做什么，再通过点击、输入和滚动操作电脑，直到完成任务。**
