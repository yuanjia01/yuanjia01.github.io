![Agent Harness 之上下文管理](/images/article-content/context-management/cover-agent-harness-context-management-handdrawn.png)

近几年，上下文窗口常被模型厂商当作新模型的重要卖点之一进行宣传。2023 年初，Claude 的窗口还只有 9K Token（K 即 thousand，千），差不多只能装下一篇近万字的小说；但到 2026 年，主流前沿模型普遍达到约 1M Token（M 即 Million，百万）的上下文窗口，体量大约接近一部《红楼梦》。三年间，容量增长了约 110 倍。

![上下文窗口的三年变化](/images/article-content/context-management/01-context-window-timeline.png)

窗口变大，模型一次能处理的信息更多；但 Agent 执行长任务时，用户要求、文件、对话和工具返回也会不断累积。

每一轮调用时，Harness 要从这些材料里组织当轮输入，并在有限容量内决定带上什么、怎样安排、哪些暂不带入。围绕这些取舍展开的，就是其中的上下文管理模块。

## 01　上下文是什么？

### 上下文、窗口与会话历史

Agent 做一项任务时，可能会多次调用模型，并在调用之间使用工具。每次模型调用前，Harness 都会准备一组信息交给模型。可以把这一过程想象成 Agent 在桌边处理一项工作：眼下要用的材料摊在桌面上，完整的沟通记录收在旁边的档案柜里，而桌面空间有限。

![窗口、上下文与会话历史](/images/article-content/context-management/02-context-window-contents.png)

桌面上的材料，就是**当前上下文，**它是模型在一次调用中实际收到的全部信息。

桌面的可用面积就是**上下文窗口**，它规定模型单次调用可处理的信息容量上限。无论是送给模型的材料（输入），还是模型生成的回答（输出），都要占用这份容量。不同模型对上下文窗口的标注方式可能不同：有的把输入和输出合并算作一个总上限，有的则分别列出。

档案柜对应产品端保存和展示的**会话历史**。它会持续保存用户和 Agent 的对话记录，但某条消息留在记录里，不代表本次模型调用一定会用到它。

### Token：窗口的计量单位

上下文窗口以 **Token（词元）**为单位计量。文字会被切分成一定数量的 Token，并占用相应的窗口容量。

人读一句话，往往按字、词和句子理解；但模型内部做的是一连串数学运算，它只会算数字，无法直接处理文字。所以文字要先由 tokenizer（分词器）切成一个个小单位，也就是 Token。每个 Token 都对应一个 token ID（数字编号），模型再把这个编号通过 Embedding（嵌入）转成一组供计算使用的数字。

![文字怎样进入模型计算](/images/article-content/context-management/03-token-processing-pipeline.png)

Token 不一定对应一个汉字或一个完整单词。它可能是一个字符、词的一部分，也可能是一个完整单词或标点。由于不同模型使用的分词器和词表可能不同，同一句话在不同模型中的切分方式和 Token 数量都可能不同。所以，1M Token 是容量单位，一般不等于一百万个汉字或英文单词——它只决定“能装多少”，至于一次调用具体装入哪些材料，则要看 Harness 如何管理上下文。

## 02　上下文管理总览

上下文管理可以看作一组围绕每轮模型调用展开的工作。Agent Harness 负责每次调用模型时，管理这一轮把哪些材料放进入上下文、放多少、怎么安排；暂时不放进来的内容如何保存、以后何时取回。

具体可以分成四个相互衔接的操作环节：

1. **收集与组装：**管理“这一轮可以从哪里取材、哪些材料值得带入、按什么顺序组织”。Harness 会围绕当前任务选取相关内容，再组合成模型输入，而不是把所有可用信息一股脑塞进去。
2. **预算与窗口：**管理有限容量如何分配。系统指令、当前请求、会话历史、检索资料、工具说明和工具返回结果都要占位置，还要给模型的输出留出空间。Harness 要据此安排优先级，内容一多，低优先级内容就可能需要调整或移出。
3. **裁剪与压缩：**管理已经进入上下文的内容怎样缩减。裁剪是局部删减，比如截短工具输出、去掉重复片段；压缩是整体重写，把较长的对话和执行过程收成一段任务状态。两者都可能丢信息，但有些信息丢了，任务就接不下去。至少要保住这几类：任务做到哪儿了、接下来要做什么、已经定下什么、不能违反什么等。
4. **外置与持久化：**管理暂时不放在模型输入里的信息如何保存、以后如何取回。上传的文件、生成的中间结果、任务的进展记录都可以留在上下文窗口之外，需要时再读回并提供给模型。存下来不等于模型知道——不取回，它就不在模型的视野里。

![四个操作环节与贯穿约束](/images/article-content/context-management/04-context-management-overview.png)

四个环节还要受访问权限和信息质量的约束。前者决定哪些资料可以被当前任务读取并带入上下文；后者则要看资料来源是否可靠、内容是否仍然有效。没有读取权限的资料不应被取用；资料过期、存疑或彼此冲突时，则可能需要排除、标注或进一步核实。比如，检索到一份内容相关但已过期的制度，不该直接作为当前依据。

这四个环节里，收集与组装和裁剪与压缩直接决定模型这一轮看到什么，接下来两节将进行详细介绍。预算与窗口是它们共同的容量前提，会在其中一并提及。外置与持久化管的是上下文之外的内容，将在后续文章单独介绍。

## 03　上下文管理之收集与组装

四个环节里，收集与组装决定这一轮模型看到什么、按什么顺序看到，也最影响单次调用的效果。

这一步的对象，是可能进入本轮上下文的材料，通常包括以下几类：

- **系统提示词（System Prompt）**：产品或 Agent 系统预先设定的指令，保存在产品端，不进会话历史。每次调用时 Harness 都会把它放进当前上下文，用来给模型定身份和行为边界——扮演什么角色、遵守哪些规则。用户通常看不到它的完整内容。
- **用户提示词（User Prompt）**：用户当前输入的问题、指令或任务要求。它随本轮请求进入上下文，只在提出的这一轮充当“当前指令”，从下一轮起就变成历史消息的一部分。若系统提示词和用户提示词要求冲突时，Agent 通常应优先遵循系统提示词。
- **历史消息**：之前的用户提问和模型回复。Harness 只会挑出与本轮任务相关的部分带入上下文，不会把整段会话都塞进去。这样模型能接上之前的讨论，用户不必每轮都从头交代。
- **文件与资料**：例如上传文档中的片段，或本次任务会用到的外部参考内容。模型自己不知道的事实，要靠它们带进来。
- **工具说明、调用与结果**：工具说明告诉模型可调用哪些工具、参数如何填写；调用和结果记录则说明上一步做了什么、做成了什么。它们决定模型下一步能做什么。
- **Skill（技能）指令**：即可复用的操作步骤。需要时，这些步骤会进入上下文，让模型照流程办事，不必每轮重新摸索。

每次调用时，Harness 会从不同来源收集材料：系统提示词、Skill 指令和工具说明通常由产品预先准备；用户当前提出的任务随本轮请求送入；历史消息和文件资料根据当前任务按需查找；工具结果则要等工具执行后，才会进入后续调用。

为了控制上下文的大小，收集到的材料不会全部进入本轮请求。Harness 会先挑出与当前任务相关的部分，长文件只取有关段落并保留出处；再判断它们能不能用——来源是否可信、当前用户是否有权访问、版本是否最新、是否已经过期等。互相矛盾的材料，按来源、版本和时效判断哪份更适用；实在分不清，就把冲突原样标注出来。最后，按窗口的剩余容量决定实际带入多少材料。留下的这些，就被 Harness 组成模型本轮要接收的输入。

例如，要核对一份报表里某个指标为何变化，Harness 会先取当前版本的口径说明，只选出与指标有关的段落并保留出处。如果模型发现还需要算差额，再请求调用计算工具。Harness 执行后，把结果连同必要背景放入下一次调用。这样，每一轮送入模型的材料都会随任务进展而改变。

## 04     上下文管理之裁剪与压缩

材料进来了，却不会一直留在上下文里。任务越往后推进，积累的对话和工具结果越多，迟早会超出窗口容量。**这时就要让一部分材料离开，方式有两种：**一种是直接移除，这就是**裁剪**——比如较早一轮的工具返回已与当前问题无关，后续便不再带上，很好理解；**压缩则不同，也更值得留意。**它会把较早过程整理成摘要，让摘要代替一部分原始内容，供后续调用继续使用。它不像 ZIP 文件——解压后能恢复原文；Agent 的上下文压缩通常是有损的。

压缩更像一次工作交接。系统把较早的对话和执行过程整理成一张交接单，尽量留下后续工作离不开的信息，如任务做到哪儿了、接下来要做什么、已经定下什么、不能违反什么等。最近几轮内容则可能继续保留原文，刚发生的内容最需要准确，压成摘要反而容易丢细节。下一轮模型收到的，不再是全部原始过程，而是「交接单 + 近期内容 + 当前问题」。

交接单能让任务继续，但也要求系统不断取舍：删什么、何时摘要、最终留下什么。假设任务是把一份报告“精简一些，但不要删减其中任何数据”。如果压缩后的摘要只留下“精简报告”，漏掉了“不要删减数据”这条限制，下一轮模型就可能删掉数据。摘要还可能把限制改错，比如把“不能删数据”写成“不要改数据格式”。这两种摘要读起来都通顺，意思却变了。如果原话已经被摘要替代，后续模型能依据的就只有摘要里的内容。因此，压缩后需要检查关键限制是否被保留下来。

## 05　常见 Harness 压缩实现

Agent 产品通常会自动压缩，但方式可能并不相同。本文基于 DeepSeek Harness 和 Codex 公开的源码，对比二者的压缩实现路径。两者都在为长任务腾出空间，但关键步骤的先后不同。

### DeepSeek Harness：裁剪优先

DeepSeek Harness 的 `compaction-basic` 有两种启动压缩的时机：一种是在调用模型之前，按所选模型的窗口容量和配置检查 Token 用量，达到预设压力线便提前介入——这时窗口未必已满，但已经到了系统提前处理的节点。

这时，如果系统配置了工具结果裁剪器，Harness 会先缩短过长的搜索结果或日志，再重新计算 Token 用量。用量降回触发线以下，就不必再做摘要压缩；如果仍超线，才把一部分较早的执行过程整理成 **Checkpoint**（阶段性交接摘要），并尽量保留近期步骤。

另一种情况是，请求已经发给模型服务，对方明确返回“上下文超限”。这不是提前判断窗口快满，而是这次请求已经被拒绝。Harness 会进入超限后的恢复流程：如果配置了裁剪器，就先裁剪工具结果，再压缩历史；压缩成功后重新尝试请求。与前一种情况相比，这种处理不再等待预设触发线，而是优先腾出空间让任务恢复。

![DeepSeek Harness 压缩路径](/images/article-content/context-management/07-deepseek-compaction-flow.png)

### Codex：摘要优先

Codex 的 `compact.rs` 在压缩启动时会先生成一份交接摘要，尽量留下当前进展、关键决定、重要限制、未完成事项，以及继续工作需要的资料。

摘要成功后，系统从较早的执行记录中按容量预算选取部分真实用户消息，与摘要一起重组成更短的历史。至于最初的系统规则等上下文，可以随压缩结果一起放回，也可以留到下一次普通调用时再恢复。

如果历史太长，连摘要请求都超出上下文窗口，Codex 就会从最早的历史记录开始删减，再重新请求摘要；它会尽量保留较新的对话内容。

![Codex 压缩路径](/images/article-content/context-management/08-codex-compaction-flow.png)

两种实现都不是把聊天记录无损缩小，而是在有限容量内重排任务所需的信息。DeepSeek Harness 会先裁剪能按规则缩短的工具结果，再判断是否需要摘要；Codex 则先生成任务摘要，再按预算保留部分原始用户消息。前者先处理可确定删减的材料，后者先整理任务状态。它们的差别说明，**压缩没有一条脱离任务形态的固定顺序：先处理什么，取决于系统准备优先保护什么。**

## 06　小结

上下文管理不只是一个技术问题，也影响我们平时怎么用。

对一个 Agent 来说，上下文管理的核心其实很简单：腾出空间时，别把关键信息弄丢。无论裁剪还是压缩，取舍都会发生，所以它需要能回看当时带了什么、能核对关键限制还在不在、出错能回到之前的状态。

个人使用中，我们也可以主动管理上下文。Token 对应真实的成本，无关文件如果反复带入就会导致使用成本增加。

具体可以从几件小事做起：

- 一个会话只围绕一个目标；目标变了，就新开一个会话。
- 长任务完成一个阶段后，把结果和下一步整理成明确摘要；需要时再让 Agent 读取。
- 上下文占用较高时，可以主动压缩。压缩前写下不能丢的限制，压缩后让 Agent 复述对照，确认目标、限制和下一步都还在。
- 给 Agent 提供文件或日志时，只选取与当前问题有关的部分，避免无关内容反复占着上下文。

**主动管理上下文，就是把有限的容量和真实的成本，用在仍然需要推进的工作上。**
