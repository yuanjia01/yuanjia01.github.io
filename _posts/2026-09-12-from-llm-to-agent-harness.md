作者：圆仔

最近，我用 Dify 搭了一个报销审核助手。输入报销制度和费用明细后，它可以识别超标项目、疑似重复记录，也会在制度信息不足时明确回答“无法判断”。搭着搭着，我冒出一个问题：这样一个助手，和最近总听人提起的 Agent（智能体），到底差在哪？

![AI 报销审核助手：输入报销制度和费用明细，输出审核结论](/images/article-content/harness05/expense-assistant-overview.png)

先说这个助手是怎么工作的：把规则写进提示词，交给**大语言模型（LLM）**，让它照着流程跑一遍，输出结论。这种“模型照着人定好的流程干活”的用法，业内叫**工作流（Workflow）**，可以粗略概括成：**工作流 ≈ 模型 + 固定流程**。

那 Agent 呢？这就要先说到 **Harness**。它本意是马具——马具不替代马奔跑，但决定它往哪儿跑、什么时候停。放在 AI 里，它指的就是模型之外那套控制系统。**DeepSeek 给出了一个公式：Agent = Model + Harness**。两个式子摆在一起，差别就出来了：模型还是那个模型，变的是模型外面那套系统——工作流里，它是写死的流程，每步做什么开工前就定好了；Agent 里，它叫 Harness，允许模型拿着新结果自己选下一步。所以，搞懂了 Harness，就搞懂了工作流和 Agent 的区别。**DeepSeek 在 2026 年 8 月开源了 DeepSeek Harness**，一经发布就吸引了业界广泛关注。上线仅一个多月，**GitHub 上已收获超 22 万 Star。**本文就以它为样本，把它拆开看看，最后再回到这个报销助手，看看它和 Agent 到底差在哪？

## 01 Harness 的整体架构：模型外面究竟有什么

如果把模型比作驾驶员，Harness 更像车辆中围绕驾驶行为运行的整套系统：导航负责提供信息，方向盘和传动系统把判断变成动作，刹车与安全规则限制风险，仪表盘记录运行状态。驾驶员负责判断，但只有驾驶员还不够；判断要通过这些部件，才能成为一次可执行、可约束、可追踪的行程。

Harness 也不等同于常说的 Agent 框架。**框架是开发者用于搭建 Agent 的通用工具箱**，通常提供状态、节点、消息、工具或多 Agent 协作等编程抽象；**Harness 是某个 Agent 实际运行时包围模型的完整控制系统**，除了编排代码，还包括具体的上下文策略、工具实现、权限、会话、日志和停止条件。一个框架可以搭出多套 Harness；一套 Harness 也可能同时包含框架、自研代码和外部服务。

DeepSeek Harness 这样的项目，既是一个用于搭建 Harness 的开发框架，也提供了一套可直接运行的默认 Harness 实现。本文关注的是后者——它实际运行时的模块组织和运行流程。

Harness 目前还不是边界完全统一的标准术语，不同系统的模块名称和切分方式各不相同。为了便于理解运行职责，本文从功能角度，将 Harness 通常包含的内容归纳为**八个主要部分**。

| 模块 | 具体负责什么 | 缺失后可能发生什么 |
| --- | --- | --- |
| 模型适配 | 统一不同模型的请求、流式响应、Tool Calling 和错误格式 | 更换模型时需要重写上层逻辑 |
| 系统提示词与上下文组装 | 选择本轮需要的目标、规则、历史、知识、文件和工具说明 | 模型看不到关键信息，或被无关内容挤占窗口 |
| 工具与运行环境 | 注册工具、描述参数，并在 API、浏览器、文件系统或沙箱中执行 | 模型只能提出建议，无法获取实时信息或改变外部状态 |
| Agent Loop 与任务控制 | 决定何时请求模型、执行工具、继续、重试、等待或停止 | 任务只能单次回答，或陷入无意义循环 |
| 会话、记忆与压缩 | 保存过程状态，并在上下文有限时选择保留、检索、摘要或压缩 | 多步任务失去前因后果，长任务超出上下文窗口 |
| 权限、审批与沙箱 | 限制工具、路径、网络和高风险操作的执行范围 | 错误判断可能直接变成现实损失 |
| 错误恢复 | 处理超时、无效参数、工具失败、取消和人工接管 | 一个局部故障可能让整项任务中断 |
| 可观测性与评估 | 记录输入、模型调用、工具结果、耗时和成本（可观测性）；定义任务完成标准并对比实际效果（评估） | 结果出错时无法定位，也无法判断任务是否真正完成和持续优化 |

这八个模块既是并列的功能分类，在运行时又可以归为**三类职责**。

第一，模型适配和上下文组装负责“准备本轮模型调用”。

第二，工具、环境和权限负责“把模型判断变成受控行动”。

第三，Loop、会话、恢复与可观测性负责“推动任务继续，并在出错时定位和恢复”。

因此，Harness 的核心并不是模块数量，而是把四件事连接成闭环：**模型看见什么、模型能够做什么、执行后发生了什么、系统接下来怎么办。**

![Harness 八个模块在运行时归为三类职责](/images/article-content/harness05/harness-architecture.png)

## 02 Harness 如何执行一项任务

前面讲的是模块，接下来看它们怎么跑起来。假如用户提出这样一个需求：“帮我规划本周末的杭州两日游，查询天气、比较交通方案，再把确定后的安排写进日历。”Harness 通常会执行下面这六步。

![Harness 六步协作流程，以及进入下一 step 的反馈回路](/images/article-content/harness05/agent-runtime-flow.png)

第一步是**接收目标并建立运行状态**，主要涉及会话以及权限策略。系统不只保存用户原话，还可能绑定用户身份、当前会话、工作目录、预算、截止时间、允许使用的工具和权限策略。这些信息决定任务在哪个边界内运行。

第二步是**组装上下文**，主要由系统提示词与上下文组装、会话、记忆与压缩模块共同完成。Harness 从系统提示词、对话历史、检索结果、文件内容和工具的 JSON Schema 中，选择本轮真正需要的信息，组成发送给模型的请求。这里的关键不是“把所有资料一股脑塞进去”，而是取舍：什么必须保留，什么可以摘要，哪些工具此刻应该对模型可见。模型并不是自动知道一切，它只能看到 Harness 放进这次请求里的内容。

第三步是**调用模型并解释输出**，主要由模型适配模块负责。它把组装好的上下文转换成具体模型能够接收的请求，再统一处理不同供应商返回的文本、Tool Call、拒答或异常响应。模型可能直接生成最终答案，也可能选择天气工具，并给出城市、日期等参数。

第四步是**校验并执行工具**，主要由工具与运行环境以及权限、审批与沙箱模块负责。Harness 检查工具是否存在、参数格式是否正确、当前权限是否允许，必要时请求用户批准，再把调用交给实际运行环境。这些调用也可能落在沙箱里执行：即使模型提出危险操作，执行边界仍由系统强制约束。模型负责选择行动，Harness 才是发出 API 请求、读取文件、控制浏览器或运行命令的一方。

第五步是**把结果写回会话**，主要由会话和可观测性模块负责。天气 API 返回的数据会以 **Tool Result** 或 **Observation（观察结果）** 的形式进入会话，同时记录成功、失败、耗时和错误。模型下一次看到的不是它对天气的猜测，而是工具真正返回的结果。只有完成这一步，外部世界的新状态才会变成下一次判断的依据。

第六步是**继续、暂停或停止**，主要由 Agent Loop 负责，遇到异常时错误恢复机制也会参与。如果天气已经查到、交通还没比较，Harness 会组装包含新结果的下一次上下文，再次请求模型；如果模型给出最终方案且没有新的工具请求，本轮结束。系统也可以因为达到步数、时间或成本上限，遇到不可恢复错误，等待用户批准，或被用户取消而暂停。这条流程并不是严格线性的：如果决定继续，第六步就会回到第二步，重新组装上下文并发起下一次模型调用。

这条交替链路经常用 **ReAct** 来解释。ReAct 取自 Reasoning 和 Acting 的拼合，可以理解为让系统在“判断下一步—执行行动—观察结果”之间交替推进：模型先基于当前信息选择动作，外部环境执行并返回 Observation，模型再利用新证据继续判断。

但 ReAct 只是常见组织方式之一，不是判断 Agent 的唯一标签。也可以先由模型生成计划，再由执行器逐项完成，即 **Plan-and-Execute**；可以先由路由器判断任务类型，再进入不同工作流，即 **Router**；也可以让多个 Agent 分工协作。无论采用哪种形式，Harness 都必须明确三个问题：**当前状态是什么，谁有权决定下一步，什么条件代表任务应该停止。**

## 03 DeepSeek Harness 如何实现这些模块

前面介绍了 Harness 通用的八个模块。落到 DeepSeek Harness 的源码里，这些职责具体怎样组织？答案是插件化。

DeepSeek Harness 最鲜明的架构原则是 **Everything is a Plugin（一切皆插件）**。它底层使用 Cordis 组织插件；模型适配器、工具注册表、会话日志乃至 Agent Loop 本身，都作为插件挂载到共享上下文中。

说人话就是，它没有把所有能力焊死在一个大程序里，而是更像一套乐高积木：每个插件是一块功能积木，系统启动时再按照配置把它们拼起来。需要替换模型、增加工具或更换存储方式时，只调整对应的积木及其配置，不必把整套系统推倒重来。

插件虽多，但真正撑起一次“模型—工具”循环的是其中六个**核心包**。官方架构文档列出的这六个包，在运行链路中的作用如下：

| DeepSeek Harness 模块 | 在运行链路中的作用 | 通俗解释 |
| --- | --- | --- |
| `llm` | 屏蔽不同模型供应商和响应格式的差异 | 像适配器，让上层不用分别理解每家模型的接口 |
| `system-prompt` | 收集提示词片段和工具说明，生成本轮系统提示词 | 像备课，把本轮需要的规则和工具说明整理好 |
| `tools` | 注册工具，并串起执行前检查、执行和结果处理 | 像工具台，登记可用工具并负责受控执行 |
| `session` | 保存只追加的事件日志，并由日志派生模型可见的历史消息 | 像任务档案，按顺序保存过程与结果 |
| `agent` | 定义 Agent 的接口、运行状态和相关事件 | 像运行说明书，规定 Agent 的接口和状态 |
| `agent-loop` | 驱动 turn、step、模型请求和工具执行 | 像调度器，串起模型请求、工具执行与停止判断 |

对应前面的八个通用模块，这六个核心包主要覆盖模型适配、系统提示词与上下文组装、工具执行、Agent Loop，以及会话状态和事件记录；权限、审批、沙箱、持久化、记忆压缩、更完整的错误恢复、遥测与评估等能力并没有全部塞进核心包，而是由外围插件按需补齐。**也就是说，核心包搭起最小运行主干，可选插件继续补上可靠性与产品化能力——Agent Loop 负责让任务向前运行，但上下文、工具、会话和安全边界共同决定它能否可靠运行。**

插件化带来的是可替换性和扩展能力。例如，代码 Agent 和资料研究 Agent 可以共享同一套会话与循环机制，只是挂载的工具不同；本地文件系统也可以换成远程沙箱。但插件越多，依赖关系、配置和兼容性管理就越复杂。DeepSeek Harness 目前处于开发者预览阶段，官方明确提示后续可能出现不兼容变更，因此更适合作为可研究的参考实现，而不是已经定型的行业标准。

插件化解决了“模块怎么组织”，那运行时这些模块如何协作？下图根据官方架构文档整理，展示了六个核心包在一次循环中的协作关系：

![Agent Loop 驱动 DeepSeek Harness 核心包协作：根据固定版本官方架构文档整理](/images/article-content/harness05/deepseek-plugin-tree.png)

图中深色的 Agent Loop 是运行时的驱动器。它不负责模型推理、工具执行或日志保存，却负责让这些模块按顺序协作：从 `session` 领取输入，让 `system-prompt` 组装上下文，通过 `llm` 请求模型，把 Tool Call 交给 `tools`，再把结果写回 `session`。只要还有结果等待处理，循环就会再次开始。

## 04 Dify 实践：Workflow 与 Agent 的控制权

拆完了 Harness 的模块和运行链路，再回头看开头那个报销助手——它是固定 Workflow 的典型样本：执行路径由设计者预先确定，模型只负责其中一个环节。同样具备模型调用、上下文模板、节点执行这些 Harness 类能力，它为什么还算不上 Agent？

这要从 LLM 最基础的运行方式说起。LLM 的一次调用，是“输入 → 模型 → 输出 → 结束”：把上下文交给它，它给出结论，过程就结束了——它不会自己执行工具，也不会自己发起第二次调用。很多人第一次接触 **Tool Calling（工具调用）** 时会以为是模型自己调用了工具，其实模型只是生成了一段“调用意图”，真正执行工具、把结果放回下一次请求的，是模型外面的 Harness。Agent 则围绕目标持续运行：模型判断下一步，Harness 执行行动、把真实结果写回，模型再基于新证据继续判断，形成“判断—行动—观察—再判断”的闭环。

现在看报销助手实际跑起来的样子。当前流程由三个节点组成：用户输入报销制度和费用数据，LLM 节点完成审核，输出节点展示结果。我分别测试了资料完整和缺少交通费标准的两组数据，模型都按照提示词给出了符合预期的结论。

![Dify 报销审核助手：用户输入、LLM、输出三个固定节点](/images/article-content/harness05/dify-workflow-current.png)

追踪页面显示，“用户输入—LLM—输出”三个节点各执行一次，没有工具调用、外部结果写回或第二次模型请求。这说明 Dify 已经提供了变量传递、上下文模板、模型适配、节点执行和运行记录等 Harness 类能力，但这条应用路径仍然由我预先画好，模型只负责完成其中一个节点。

![Dify 运行追踪：用户输入、LLM、输出各执行一次](/images/article-content/harness05/dify-trace-summary.png)

这里不能简单地用“有没有工具”判断是不是 Agent。固定 Workflow 也可以调用知识库、API，甚至包含条件和循环；Agent 也可以被限制在很窄的行动范围内。更实用的判断方法是看**运行时控制权**：下一步主要由设计者提前写死，还是由模型根据当前状态和工具结果动态选择？一句话总结就是，固定 Workflow 与 Agent 的区别不在调没调工具，而在下一步的控制权在谁手上——设计者写死的是 Workflow，模型动态决定的是 Agent。

如果我给报销助手增加一个固定的知识检索节点，路径依旧是“先检索、再审核”，它仍然更接近 Workflow。如果模型能在发现“交通费标准缺失”后，自主决定是否查询制度工具，再根据查询结果选择继续、拒答或结束，它就已经是 Agent 了。

这两种方式没有绝对高下。对于规则稳定、步骤可预期、对确定性和可审计性要求较高的任务，固定 Workflow 往往更容易控制；对于信息不完整、路径难以预设、需要多次探索的任务，Agent 才更能发挥价值。

## 05 从模型到 Agent：Harness 补上的那一环

回到开头的问题：我搭的报销助手和 Agent，到底差在哪？

你有没有发现，Agent 其实就像一个活生生的人，而模型，就是它的大脑？想象你在做饭：突然闻到一股糊味，大脑马上判断“锅烧干了”，于是指挥手去关火。闻到味道的是鼻子，动手的是手，大脑只负责中间那句判断——它自己不会伸手，也听不见声音，所有的想法都得靠身体去落地。放到 AI 里，Agent 也有自己的“手”和“感官”：手是它可以调用的工具——查数据库、发请求、写文件；感官是它接入的数据源——制度库、天气 API，甚至一个麦克风。只是这些工具和数据源，模型自己都“够不着”：它只会生成文字，不会真的伸出手去拿。

那 Harness 呢？它就是连接大脑和这些部件的整套“翻译系统”：把大脑的判断翻译成动作——想关火，就去控制手；把外界的信息翻译成大脑能懂的语言——听到的、摸到的，都变成大脑能处理的信号。所以，给模型接个麦克风，它并不会“听到”声音——只有当 Harness 把声音转成文字、把工具结果写回上下文，模型才真正“看见”、“听到”、“摸到”。

**模型负责判断，Harness 负责把判断变成行动、再把行动的结果送回判断。这正是从 LLM 到 Agent 之间，Harness 补上的那一环。**
